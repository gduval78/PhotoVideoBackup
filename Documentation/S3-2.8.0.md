# 2.8.0 — S3-compatible destination (planned)

Status: **notes only, nothing implemented** (2026-11-14). Prerequisite: 2.7.0 (profiles) is released. Check real demand first (ask Andreas and the other testers).

Goal: a profile destination `.s3` next to `.folder` and `.nas`, for cheap off-site storage (Backblaze B2, Wasabi, Cloudflare R2, AWS S3, MinIO, Scaleway…), without the iPhone-space and quota problems of iCloud Drive. **Pro**, like the NAS.

## Why it fits

- `BackupTarget` / `RemoteBackupTarget` already abstract the destination; add `S3Target` beside `SMBTarget`. Dedup (`resolveCoverage`, ledger, `.pvb-index.json`, deterministic names) is unchanged.
- **Streaming is possible** (unlike AMSMB2): multipart upload, parts ≥ 5 MB, one chunk in memory. A NAS-only-style session would no longer need a staging file on the device → `PHBackupEngine` can stream to S3 like to a local folder (`canStream`, `DiskSpacePreflight` staging branch).
- **Verification without re-download**: send `x-amz-checksum-sha256` with the upload; the server validates it. Avoids egress fees. Fallback for servers without checksum support: HEAD + size (weaker; say so in the Report) or a re-download for small files only.
- A multipart upload can be resumed (`ListParts`) after an interruption.

## Design points to decide / get right

1. **Never overwrite a different file.** A PUT replaces silently. Use `If-None-Match: *` (AWS, R2, B2 support it); for servers that do not, HEAD before PUT. Keep the "name chain" (`name`, `name-1`…) logic as is.
2. **Listing by prefix** for `existingSize`, the sidecar and Browse; no real directories. Sidecar `.pvb-index.json` is a small object at the prefix root (read/overwrite is fine on S3; strongly consistent on the major providers).
3. **Modification date** cannot be set: store it as user metadata (`x-amz-meta-mtime`) or ignore (the capture date is already in the profile name).
4. **Abort incomplete multipart uploads** on failure/Stop (otherwise they are billed); advise a bucket lifecycle rule in the guide.
5. **Credentials**: endpoint, region, bucket, prefix, access key, secret. Secret in Keychain under the profile's own account (like `profile.<uuid>.nas`); `ProfileDestination.s3(config)` + `s3SecretAccount`. A *Test connection* button (list + write/delete a small object).
6. **Library**: prefer a small SigV4 implementation over `URLSession` (path-style and virtual-hosted addressing both needed for non-AWS endpoints) rather than the heavy AWS SDK for Swift. Test against several providers (SigV4 quirks differ). Android: `minio-java` or AWS SDK for Kotlin.
7. **Cellular warning** like the NAS (reuse the mobile-data banner).
8. **Background**: `beginBackgroundTask` as today; background `URLSession` uploads need files on disk — not attempted.
9. **Report/Browse**: Browse lists S3 destinations like `nasEntries` (identity = endpoint|bucket|prefix|key id); thumbnails on demand download, as for the NAS. LUT grading on S3: out of scope at first (same download → grade → upload scheme could follow).
10. Free-tier rule unchanged: one profile free; S3 destination is Pro (`ProfileDestination` Pro gate in `ProfileDetailView.requirePro` and at run time).

## Per-provider differences (capabilities, not `if provider ==`)

Model each provider as a small capability set chosen in the editor (preset by endpoint: AWS, R2, B2, Wasabi, MinIO, **GCS**, custom): *conditional write header*, *checksum method*, *addressing style*. The engine asks the capability, never the provider name.

| Capability | AWS / R2 / B2 / MinIO | Google Cloud Storage (XML interoperability API) |
|---|---|---|
| Auth | SigV4 with access key + secret | SigV4 with **HMAC keys** of a service account (`storage.googleapis.com`) |
| Do not overwrite | `If-None-Match: *` (else HEAD first) | `x-goog-if-generation-match: 0` |
| Checksum at upload | `x-amz-checksum-sha256`, validated by the server | **no SHA-256**: CRC32C / MD5 via `x-goog-hash`; compare it with the value computed while streaming, or re-read the object |
| Multipart | S3 multipart | XML API multipart (initiate / part / complete) — same flow, check part limits |

- Google **Drive** and **Photos** have no S3 interface and stay out of scope (different API, OAuth).
- GCS is a **second-wave provider**: ship AWS / R2 / B2 / MinIO first; add GCS once the capability set exists. Its behaviour is documented from knowledge, not yet tested — validate on a real bucket (HMAC key, multipart, `x-goog-if-generation-match`, `x-goog-hash`) before listing it in the guide.
- Report wording: when the checksum is not SHA-256 (GCS, or a server without checksum support), say "verified by CRC32C/size" rather than "SHA-256". The dedup identity of the *source* stays SHA-256 (ledger); only the post-upload verification differs.

## Not in scope

S3 Glacier/Deep Archive restore flows, server-side encryption options beyond the provider default, bucket creation, scheduling.
